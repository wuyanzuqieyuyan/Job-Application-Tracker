## 0. 推荐架构结论（TL;DR）

1. **顺序持久化 = "持久化高水位计数器 + 空洞槽位恢复"模型**：
   - 新增持久化元表 `meta(key,value)`，键 `next_sort_order`（v1 的 `MAX+1` 存在高水位**复用
     已删除末位记录槽位**的漏洞——修订核心点之一）。
   - 新建/批量导入：在各自的**写事务内**从计数器分配序号并同步推进计数器；
     事务回滚连带计数器一并回滚，原子性由同一事务保证。
   - 删除：**不压缩顺序、不降低计数器**，空洞永久保留；`deleted_at` 不存在，无软删除。
   - 恢复：以删除快照里的**原 sort_order + 原时间戳**整行重建，单行事务；
     槽位被占（结构性不可能，见 §2.5）→ 唯一确定行为：从计数器分配新位降级追加。
   - 好处：分配永不复用空洞，撤销窗口内"删除末位记录再新建"不再吞掉待恢复槽位；
     恢复无锚点、无平移、无位置过期问题。
2. **位置信息的唯一来源是服务端**：`DELETE /api/jobs/:id` 从 **204 改为 200**，
   响应返回**完整快照**（五业务字段 + `sortOrder` + **原始 `createdAt/updatedAt`**）。
   前端撤销栈仅做回放，恢复后**时间戳保持删除时的原值**（见 §4.2/§4.3 语义说明）。
3. **恢复冲突契约是确定的、非幂等的**：ID 已存在 → 409 `id_conflict` 绝不覆盖；
   重复请求同样 409，**不宣称"幂等成功"**；前端收到冲突必须先重新拉取服务端列表核实，
   才能同步 UI 或关闭撤销提示（§4.4 精确规则）。
4. 前端现有行为**全盘保留**：搜索/筛选/显式日期排序/视图切换/5 秒 LIFO 撤销。
   `sort_order` 只是稳定持久顺序基座，**不替代**前端显式排序——API 默认序仅充当
   同日期记录的确定性 tie-break（替代现在的"数组序"）。
5. 显式代价（破坏性契约，当前无外部客户端）：DELETE 204→200；现有 DELETE 断言在 P4 更新。

## 2. 数据模型（任务 B.1）

### 2.1 Schema（新库）

```sql
CREATE TABLE IF NOT EXISTS jobs (
  id           TEXT PRIMARY KEY,
  company      TEXT NOT NULL CHECK(length(company)  <= 50),
  position     TEXT NOT NULL CHECK(length(position) <= 50),
  applied_date TEXT NOT NULL,
  status       TEXT NOT NULL CHECK(status IN ('applied','interviewing','offer','rejected')),
  notes        TEXT NOT NULL DEFAULT '' CHECK(length(notes) <= 200),
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
  sort_order   INTEGER NOT NULL CHECK(sort_order >= 1)
);
CREATE INDEX IF NOT EXISTS idx_jobs_sort_order ON jobs(sort_order);  -- 非唯一

-- 持久化元信息（高水位计数器等）
CREATE TABLE IF NOT EXISTS meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

### 2.2 决策与理由

| 决策 | 选择 | 理由 |
|---|---|---|
| 相同 sort_order 允许？ | **服务层不变量：不允许**；数据库**不加唯一索引** | ①计数器保证所有新增/导入路径全局唯一递增；②恢复使用"被删记录自己的历史槽位"，其唯一性等价于记录主键唯一（同 id 槽位同值），结构性无重复；③唯一索引对旧行迁移、未来平移类特性有"语句内逐行检查"互锁风险；④读取确定性由第二键 `id ASC` 兜底 |
| 读取确定性 | `ORDER BY sort_order ASC, id ASC` | 即使异常路径产生等值序号，顺序依然确定可复现 |
| `updated_at` 因纯顺序调整而变？ | 本模型**没有**纯顺序调整操作；恢复重建保留**原时间戳** | 顺序是位置元数据；保留原时间戳使"撤销恢复"在数据语义上完全不可区分于删除前的记录（详见 §4.2 产品决策记录） |
| 唯一索引的结论 | **不添加**（除非未来出现批量重排特性并先行证明兼容） | 见上；当前分配算法（计数器闭区间生成）+ 恢复算法（自身槽位）已保证无重复，测试矩阵断言兜底 |

### 2.3 高水位计数器（v2 新增核心一节）

**存储形态**（必须持久化，绝不内存）：

```text
meta 表键 'next_sort_order'，value 为十进制整数字符串。
启动时（initDb）：
  - 若 meta 表无该键：
      · 空库           → 写入 '1'（明确的初始值）
      · 非空库（迁移后）→ 写入 MAX(jobs.sort_order)+1（迁移 §3 在同一事务内完成初始化）
  - 防御性修复：若键缺失但 jobs 表有数据，按上面第二行规则重建（视为启动自愈，
    只可能因人工删库内 meta 行触发，测试矩阵覆盖重启键存在性）。
```

**事务边界与异常行为**：

| 操作 | 计数器语义 | 事务边界 |
|---|---|---|
| 新建 POST | 读计数器 n → 插入 sort_order=n → 写入 n+1 | 三语句在**同一个 `db.transaction`** 内：进程崩溃任一点前，WAL 保证要么全部生效要么全部不生效——不存在"记录插入但计数器未推进"或反过来的中间态。失败 → 500，计数器保持原值，可安全重试 |
| 批量导入 | 批内逐行分配 n, n+1, … n+k-1 → 末尾写 n+k | 在现行**整批单事务**内延伸；任一行校验失败/冲突 → 全回滚（含计数器），幂等命中行**不分配、不消耗**计数器 |
| 删除 | **不触碰**计数器 | 单语句 `DELETE … RETURNING` 原子；计数器不在其中 |
| 恢复（原槽位） | **不触碰**计数器（原槽位 ≤ 当前计数器单调不变量） | 单行事务 |
| 恢复（降级追加） | 同"新建"：分配 n 并推进 n+1 | 单事务（与 INSERT 同体） |

**重启行为**：计数器随 DB 文件持久化；重启即从 DB 读取，无内存对账问题。
并发断言：better-sqlite3 同步事务在单进程事件循环内串行，两个"读计数器→推进"事务
不可能交错（§5）。多实例同库超出当前应用范围（不承诺）。

**计数器生命周期与校验规则（v2.1 编码前约束 #1，全部确定性、无"视情况"）**：

| 情形 | 规则 |
|---|---|
| 正常启动 | 读取键值并校验合法后**直接使用，绝不重算**（不依据 `MAX(sort_order)` 推翻持久值） |
| 键值合法 | 语义：`value` 为十进制纯数字字符串、整数值 ≥ 1；**并要求 `value ≥ MAX(sort_order)+1`**（存有记录时）——这是持久不变量，任何时刻都不该被正常路径破坏 |
| 键缺失（人工删除） | **同一事务内重建**：非空表 → `MAX(sort_order)+1`（只依据现存数据，见下方边界说明）；空表 → `1`；重建动作写日志 |
| 键值非法（非数字/0/负数/溢出） | **不静默覆盖、不自动修复**：无法与历史高水位对账 → **拒绝启动**，诊断日志输出当前值与 job 表 MAX 值；人工确认后处理（本应用无该键的合法生成路径之外来源） |
| `value ≤ MAX(sort_order)`（现存值低于高水位） | **数据不一致 → 拒绝启动**并报告两边实际值（写入前的选择是"停止启动"而非静默抬升——自动修复会掩盖外部篡改或迁移缺陷；修复收敛由人工/一次性维护脚本完成，不属于本轮交付物） |
| 写入前守卫 | 消费计数器的**每个写事务内**追加断言：分配值 `n` 满足 `n ≥ MAX(sort_order)+1`（空表时 `n ≥ 1`）；断言失败 → 抛错 → **整个事务连同 INSERT 回滚** → 500 `internal_error`（防御实现 bug 或外部改库，绝不部分写入） |
| 整数上限 | 守卫上限取 JS 安全整数 `2^53-1`（better-sqlite3 将 SQLite INTEGER 读回 number；SQLite 本体上限 2^63-1 更大，对账以 JS 侧为准）：计数器到达上限 → 写事务失败回滚（计数器不推进、无部分写入） → 500。数据量级不可能达到，显式契约仅为完整性 |
| 空表 + 键缺失的边界 | 真实历史高水位在"无记录 + 无键"时**不可恢复**（已分配而未持久化的历史值无任何可观测来源）。本设计承诺的是**正常删除/创建/恢复不复用槽位**，不承诺"人为删除键后仍保留历史信息"——回退为 1 后，被删记录的槽位恢复路径本就只存在于同一撤销窗口（内存态）内，窗口外的历史槽位无可恢复引用，行为一致 |

### 2.4 各写操作对 sort_order 的处理（更新于 v2）

| 操作 | sort_order 行为 | 事务 |
|---|---|---|
| 新建 `POST /api/jobs` | 计数器分配并推进（§2.3） | 单事务 |
| 导入（新行） | 批内连续分配，末尾一次推进 | 整批单事务 |
| 导入（幂等命中） | **不分配、不消耗计数器、不改动该行** | 同上 |
| 编辑 `PUT` | **绝不触碰** sort_order 与计数器 | 单条 UPDATE |
| 删除 | 删除整行，**空洞保留**，计数器不动；响应返回完整快照 | 单语句 RETURNING |
| 恢复 | **优先原槽位**（原文 sort_order）；仅槽位被占时降级为计数器分配追加 | 单行事务 |

### 2.5 顺序语义的四象限（保留 v1）

| 概念 | 提供方 | 语义 | 与 sort_order 的关系 |
|---|---|---|---|
| 数据库默认顺序 | `GET /api/jobs`（无参数） | 记录加入的先后 | 恰是 `ORDER BY sort_order ASC` |
| 用户显式日期排序 | `SearchFilter`/`useJobs` | date-asc/date-desc | **原样保留**；API 返回序仅作同日期 tie-break |
| 搜索筛选后展示序 | `filteredJobs` computed | 过滤+排序副本 | 与数据库无关 |
| 撤销原位置 | 撤销栈 `UndoEntry` | 删除瞬间的槽位 | 快照中的 `sortOrder` |

硬性规则重申：数据库默认顺序**不得**覆盖前端显式排序；`sort_order` 不承载日期语义，
不替代 `applied_date` 排序。

## 3. 旧库迁移方案（任务 B 复核，v2 收紧计数器初始化）

### 3.1 步骤（启动时、幂等、单事务）

```text
1) PRAGMA table_info(jobs)：
     - jobs 表不存在 → 新库路径：执行新 schema（含 sort_order 与 meta 表）
                       → 写入 counter = 1 → 结束。
     - 存在但缺 sort_order 列 → 旧库路径，继续 2)。
     - 列已存在 → 跳过迁移；但需确保 meta 计数器存在（缺失 → 按 §2.3 防御性修复）。
2) BEGIN
     ALTER TABLE jobs ADD COLUMN sort_order INTEGER NOT NULL DEFAULT 0;
     UPDATE jobs SET sort_order = rowid;
     INSERT INTO meta(key,value) VALUES('next_sort_order', MAX(sort_order)+1);
     （回填后追加非唯一索引 idx_jobs_sort_order）
   COMMIT
3) 迁移失败 → 全事务回滚（DDL 参与事务，SQLite 支持事务内 DDL 回滚）→
   旧库保持迁移前状态，下次启动重跑（幂等判定重新生效）。
```

- **空库初始值 = 1（明确）**；旧库 = 回填后 `MAX(sort_order)+1`。
- 不删除旧库、不清空记录、不重命名文件；迁移只加列+建元表。
- 迁移在监听端口之前完成（挂接现状 `server.ts:7` initDb 位点）。
- 场景矩阵（空库/已有数据/部分迁移/重复启动）与 v1 一致：
  **部分迁移态不存在**（COMMIT 原子；列加但未回填/回填失错等均随 DDL 回滚消失）。

### 3.2 localStorage → 数据库顺序映射（明确：rowid ≠ localStorage 序）

- localStorage 原始数组顺序的唯一忠实映射**时机 = 导入时刻的批内顺序**：
  客户端按原数组顺序整批发送，服务端按批内序从计数器分配 `n, n+1, …`
  （空库从 1 开始）。
- 幂等重试：全部命中"同 id + 同内容"→ 跳过**且不消耗计数器**（v2 收紧）→ 顺序不漂移。
- 失败重试：整批事务非全即无（含计数器回滚）；客户端重放即可。
- 预检沿用既有结论：不符 `CLIENT_ID_PATTERN` 的记录原样保留并 UI 报告（不丢弃/不改写）；
  缺 `notes` 的记录客户端预填 `''`（服务端不静默默认；导入收到缺 notes → 400 `invalid_notes`）
  ——处理矩阵见 §4.6。

## 4. 删除与撤销恢复 API（任务 C，v2 定稿冲突/快照语义）

### 4.1 方案比较与推荐（结论不变，理由补强）

**推荐 A：DELETE 返回完整快照（含原始顺序号与原始时间戳）**。
位置是服务端顺序模型的产物，由持久化它的服务端在删除事实发生时颁发；
方案 B（204 + 前端自存）的"位置"仅是 localStorage 数组序→非服务端事实，多标签页即错位；
方案 C（软删除）引入定时清理/id 复用/恢复时限等状态机成本，单人作品集不值得。

### 4.2 删除操作契约（快照完整化）

```text
DELETE /api/jobs/:id
→ 200 { data: DeletedJobSnapshot }
   DeletedJobSnapshot := {
     id, company, position, appliedDate, status, notes,   // 五业务字段
     sortOrder,                                            // 服务端顺序号（恢复定位）
     createdAt, updatedAt                                  // 原始时间戳（恢复保留）
   }
→ 404 { error: { code: 'job_not_found', ... } }
```

- 实现：单语句 `DELETE FROM jobs WHERE id = ? RETURNING <五字段>, sort_order, created_at, updated_at`（单语句原子）。
- **created_at/updated_at 语义（明确的产品决定）**：快照携带删除时刻的原始值，
  恢复时**原样保留**。理由：撤销的产品意图是"当刚才什么都没发生"——
  时间戳重置会让恢复后的记录在"最近新增"或"最后编辑"上凭空移动；
  保留原时间戳使撤销在数据语义上完全无损。**备选（重置为恢复时刻）被否决**，
  若未来产品要求区分"曾被删除"需引入额外字段，不属于本契约。
- 删除与"顺序压缩"不在同一事务——**不存在压缩**；计数器不动。
- 幂等性：非幂等。同一删除请求重复执行 → 第二次 404（契约如实：不宣称幂等成功）。

### 4.3 恢复操作契约（冲突规则确定性）

```text
POST /api/jobs/restore
请求体 { record: DeletedJobSnapshot }     // 必填 9 个字段；缺失 → 400 invalid_request
→ 201 { data: { id, ...五字段, sortOrder, restoredAs: 'original' | 'appended' } }
错误（确定的，无"视情况"分支）：
  400 invalid_id / invalid_company / invalid_applied_date / ... / invalid_request
      // id 命中 CLIENT_ID_PATTERN；五字段走 validateJobInput；
      // sortOrder 仅在为原槽位恢复时读取（见流程 3）；时间戳格式非法 → 400 invalid_request
  409 { code: 'id_conflict' }   // 目标 id 已存在：绝不覆盖、绝不部分写入
```

**恢复流程（单事务，行为完全确定）**：

1. 结构校验：9 个字段齐全、类型正确 → 否则 400 `invalid_request`。
2. 业务校验：`CLIENT_ID_PATTERN` + `validateJobInput`（与创建同一套）。
3. `SELECT 1 FROM jobs WHERE id = ?` → 已存在 → **409 `id_conflict`**（no overwrite）。
4. `SELECT 1 FROM jobs WHERE sort_order = record.sortOrder`：
   - 空闲 → INSERT 原槽位（sort_order 也采用快照值）→ `restoredAs:'original'`；
   - 被占 → **唯一确定行为：从计数器分配新序号追加** → `restoredAs:'appended'`
     （见 §2.5 结构性不可能的分析，此处规则仅为未来特性防御；不允许 409/丢弃/静默改写原值以外行为）。
5. INSERT 携带快照原始 `createdAt/updatedAt`。提交。

**结构性不可能论证（为什么"槽位被占"正常流程不会发生）**：
计数器单调递增且永不回退（删除不降）；追加/导入只消费计数器（>全体现存历史 slot）；
原槽位恢复只由**该 id 自己**重新占用自己的历史空洞——它的所有者（同 id）在还在库内时
被流程 3 拦截。除"未来引入批量重排/手动改 meta"外，占用分支不可达。

**防御分支的定位与硬条件（v2.1 编码前约束 #2）**——槽位冲突分支**不是常规恢复路径**，
若在测试或运行中出现即意味着：数据被外部修改、迁移不完整或实现缺陷。因此：

1. 降级追加的目的是**保护数据**（绝不覆盖/绝不丢快照），**不是掩盖顺序分配缺陷**——
   该分支触发时必须同步在服务端日志中留诊断痕迹（日志内容不含用户敏感字段亦可）。
2. 降级追加的顺序号**必须由计数器在同一事务内分配并推进**（与恢复 INSERT 同事务、
   同回滚单元）；禁止以 `MAX+1` 之类的独立算法点发（那会重新引入 v1 漏洞）。
3. 响应返回 `restoredAs:'appended'`，**前端展示信息性提示**（如"原位置已被占用，
   记录已追加到列表末尾"），不视为错误样式；快照数据完好不用。
4. 测试必须证明冲突触发时：**不覆盖任何记录、不丢失快照内容、不破坏计数器**
   （计数器在被占用分支与正常追加分支消耗后保持与"新建"路径等速单调），见测试 #12/#28。
5. 数据库不变量测试（新增）：**在"创建 + 批量导入 + 恢复（含降级）"混合执行后，
   断言不存在任何重复 `sort_order`**（集成测试层面守护非唯一索引决策）。

### 4.4 前端冲突处理与重试契约（v2 明确）

收到 409 `id_conflict` 后，前端**必须执行确定序列**：

1. `GET /api/jobs` 重新拉取服务端当前状态（不得信任本地推断）。
2. 若响应中**确实存在**该 id → 这次恢复已被服务端事实取代：
   - 关闭撤销提示，向用户做信息性说明（例如"该记录已存在，已为你展示最新列表"），
   - 不展示"恢复成功"样式的 Toast；撤销条目可安全出栈（该项恢复已不可重复成功）。
3. 若响应中**不存在**该 id（极小概率：并发窗口内被再次删除/服务端刚发生其他写）→
   - **不**关闭撤销提示、**不**标记成功——提示用户"服务器状态与刚才不一致，请重试"，
   - 撤销条目保留；窗口剩余时间继续倒数，超窗自然失效。
4. 5xx/网络失败：同 3——**保留快照、不宣称成功、不误报**；窗口到期自然失效。
5. 重复提交同一恢复（第二次 409）：同流程 1–2，绝不宣称"幂等成功"。

### 4.5 锚点方案比较（保留 v1 结论）

| 方案 | 并发删除 | 连续删除/撤销 | 锚点已删除 | 锚点已移动 | 刷新/多标签 | 评价 |
|---|---|---|---|---|---|---|
| 前端原始数组索引 | ❌ 服务端状态变化即错位 | 需钳位 | 不适用 | 不适用 | ❌ | 纯本地应用专用，API 化后不可靠 |
| 前后邻居双 ID | 复杂（两键+平移+去重） | 复杂 | 需退化算法 | 需重解析 | 需开放还原语义 | 复杂度转移到恢复事务 |
| 单一 anchor ID | 同上较轻 | 同上 | 需钳位 | 同上 | 同上 | 仍是"滑动系统" |
| **持久化序号槽位（本推荐）** | ✅ 计数器单调不可占他人槽 | ✅ 各自独立槽位 | ✅ 无锚点，槽位即锚 | ✅ 槽位不可移动 | ✅ 快照自足 | 单人作品集最简正确解 |

"前端索引不能在服务端状态变化后被无条件当作准确位置"——它不再进入恢复请求，
仅保留为本地 API 失败时的只读回退语义；服务端的定位语义来自删除快照中的 `sortOrder`。

### 4.6 预检/异常处理矩阵（4.4 之外的迁移面）

| 场景 | 处理 | 层级 |
|---|---|---|
| 历史 ID 不符 `CLIENT_ID_PATTERN` | 客户端预检：**原样保留记录**并在 UI 上报；服务端收到 → 400 `invalid_id`（绝不静默丢弃/改写） | F/API |

### 4.7 撤销窗口（保留 v1）

- 撤销状态仅前端内存；5 秒窗口到期记录已真删、不可恢复（产品语义）；
- 刷新即全失效；不持久化撤销栈；
- 服务端零动作，不做软删除、无定时清理、无后台队列。

## 5. 事务边界与并发（任务 D，v2 微调）

**基本事实不变**：better-sqlite3 同步事务在单进程事件循环内串行（第二个请求的事务
只能等第一个跑完），"读计数器→插记录→写计数器"三语句不为并发请求所打断；
多进程/多实例同库不在承诺范围。

| 写操作 | 事务边界（实现规格） |
|---|---|
| 新建记录 | 单事务（读计数器 → INSERT → 写计数器） |
| 导入（含 localStorage 迁移） | 整批单事务（批内序号 + 计数器一次推进；命中行不消耗） |
| 删除 | 单语句 RETURNING 原子；计数器不动 |
| 恢复 | 单行事务（校验 → 存在性/槽位检查 → INSERT；降级时含计数器推进） |
| Schema 迁移 | 单事务含 DDL + 计数器初始化（§3.1） |
| localStorage 历史导入 | 走 import 事务；客户端重放 = 无破坏重放 |

**异常场景矩阵（谁解决什么，v2 补"计数器中途异常"）**：

| 异常 | 谁解决 | 手段 |
|---|---|---|
| 两请求同时新建 | SQLite + 单进程同步序列化 | 各自消费计数器，串行原子 |
| 两请求同时删不同记录 | 同上 | 串行成功 |
| 同一删除重复执行 | API 契约 | 第二次 404 |
| 同一恢复重复执行 | API 契约 + 前端（§4.4 序列） | 409；前端先核服务端事实再同步 UI |
| 恢复时 ID 已存在 | API 契约 | 409 `id_conflict`，绝不覆盖 |
| 计数器推进中途异常（断电/抛错） | SQLite 事务 | 同事务回滚（记录与计数器同时还原）；重启从 DB 读取，无对账 |
| 槽位冲突（结构性排除） | API | 唯一确定行为：降级追加（restoredAs:'appended'） |
| 数据库写入失败 | SQLite + 统一错误层 | 回滚 → 500 `internal_error` 不泄露细节 |
| 顺序调整中途异常 | **设计消除**（无平移语句） | — |
| 数据迁移中途失败 | SQLite | 全事务回滚，下次启动重跑 |
| localStorage 迁移失败/重试 | 服务端事务 + 幂等/计数器 | 重放全命中且不消耗计数器 |
| 前端快照过期 | 前端状态管理 | 快照只作回放；撤销失败不误报、不静默清快照（§4.4） |
| 多标签页旧位置 | 服务端 | 位置只来自删除快照；槽位不可被他人占用 |

## 7. 前端接入设计要点（下一阶段输入，仅规格）

1. Job 类型扩展：撤销相关的**快照类型**（`DeletedJobSnapshot`）新增 `sortOrder/createdAt/updatedAt`；
   列表/单条 `Job` 类型扩展只按 P5 需要最小化（GET 列表本身可不含 sortOrder——
   默认序即 sort_order；显式日期排序依旧在前端进行）。
2. `useJobs` 改造点：
   - `loadJobs()` → GET（失败回退 localStorage 只读，不清空）；
   - `deleteJob` → DELETE，**响应快照整体入撤销栈**（替代本地数组序）；
   - `restoreJob` → POST restore + §4.4 确定序列（409 必先核实服务端）；
   - `removeJobById`（撤销"新增"）→ DELETE 同 API + 内容校验改为比对服务端记录；
   - localStorage 首次导入：客户端预检 + 按原数组顺序整批 import；成功后本地键保留只读备份。
3. 撤销栈内的 `add` 类型条目仍用五字段快照（无需服务端位置）。

### 7.1 localStorage 迁移：只读盘点、备份与完成标记（v2.1 编码前约束）

**禁止预设旧数据合法**——迁移执行前必须完成**只读盘点**，把每类异常数量如实呈现给用户：

| 盘点项 | 说明 |
|---|---|
| 总记录数 | 当前 localStorage 数组长度 |
| 重复 ID 数量 | 同 key 内重复出现的 id 及次数 |
| 不符 `CLIENT_ID_PATTERN` 的记录 | 原样保留并在 UI 报告，不丢弃/不改写 |
| 缺失或无效 `notes` | 计数呈现；导入前由客户端预填 `''` |
| 缺失 company/position/appliedDate 或非法 status | 计数呈现；此类记录**无法直接导入**（服务端 400）——UI 明示将跳过的记录，不静默 |
| 与服务端既有记录冲突（同 id 异容） | 迁移批量导入会 409 回滚 → 导入前提示用户选择处理方式（跳过该条/取消迁移），决策落在**导入前的 UI 流程**，不得在导入事务内静默取舍 |

**备份与完成标记（安全重试链条）**：

1. 迁移**前**：将 `jobtrack.jobs.v1` 原始值整体快照到独立备份键
   （如 `jobtrack.jobs.v1.backup-<时间戳>`，只写不改）——原始数据从此永不丢失。
2. 触发整批 `POST /api/jobs/import`（批序 = 原数组顺序；计数器分配落库）。
3. 导入返回 201 后，客户端**核对数量与关键字段**（逐条 id + company + appliedDate 对账，
   符合"已存在→跳过、新增→创建"的幂等模型）；核对通过 → 写入"迁移完成"标记；
   任何一步失败/回滚 → **不得**写完成标记、**不得**清除原 `jobtrack.jobs.v1` 键。
4. 完成标记写完后，原键**保留为只读历史备份**（不清除），仅停止被前端作为主数据源读取。
5. 重试语义：由于服务端幂等 + 计数器命中不消耗（§2.3），任何时点重放同一批都安全，
   顺序不漂移、无重复。
